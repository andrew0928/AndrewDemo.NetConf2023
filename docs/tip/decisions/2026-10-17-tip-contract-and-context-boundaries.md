## 背景

使用者以 AndrewShop prototype 演練 TiP，目的是歸納可重用的設計 best practice。前一輪將需求與 14 條核心 AC 整理成八項架構議題，其中部分已深入保證機制、儲存方式與基礎設施選擇。

使用者確認：研究應在原則確定後停止深入，將具體機制交由實作端決定。本決策對齊 [project roadmap](../../project-roadmap.md)，承接既有物件分類與 AC，不重新決定已接受的預期行為。

## 決策

### 1. 在系統服務介面保證身分與用途不可變

- 已分類為用途不可變的 Order、Member、Cart、Checkout、Token，在最低層系統服務介面將 `id + type` 視為 immutable。
- 此處 `type` 指正式／測試用途，尚未指定程式欄位名稱或 enum。對同一物件身分，後續取得的用途必須與先前一致；此規範不要求從 ID 字串編碼解出用途。
- 具體保證機制由實作端決定；誰能 create、如何授權，由應用端介面設計決定。
- 其他合法業務欄位仍可依規則變更。實體資料儲存與更新防護機制列為實作議題，本輪確認規範即可。

### 2. 以事件或任務交接區分執行責任

- 對 AC-TIP-012 的查詢與系統到期整理，界定兩端交換工作的邊界，以 event-driven、task queue 或同類機制隔離兩端。
- 研究在交接與責任邊界確定後收斂；queue 產品、部署方式、worker 與持久化細節交由實作設計。
- 延續既有 AC：正式預約到期整理依自身責任正常執行；test 訂單衍生事件及重試仍屬 test。交接邊界本身不改變業務用途，具體 context 承接契約與傳遞機制留給後續規格及實作。

### 3. Context 延續到出口，對外結果採一致語意

- Context 須延續到系統內最後一個步驟，在離開系統前用於判定，跨出邊界後以明確的 header／result code 等契約傳遞用途與結果。
- 系統邊界為 HTTP API 時，由 HTTP middleware 統一處理對外表達；具體 header 名稱、result code 與 mapping 尚未定案。
- 內部判定、對外結果與呼叫端識別應具有一體性。既有「商業效果發生前控制」仍適用，出口處理承接已執行的判定與結果。
- Context 已依同日補充區分為下述兩類。架構確保資訊正確傳遞，涵蓋 event／async 邊界；應用端確保每個相關環節依 context 執行已定政策，在商業效果發生前完成判定。完整應用政策矩陣留給後續規格。

#### 同日補充：current identity 與 current transaction

使用者將 test 行為的判斷依據區分為兩類 context 描述：

| Context | 定義 | 對應用途 |
|---|---|---|
| current identity | 目前執行操作的身分，以及該身分／憑證是否具有 test 標記；可能來自 Member、API access token，或系統排程的工作身分。 | 改價格等操作可依此判定是否屬 test 行為。 |
| current transaction | 目前執行流程所處理的交易主體及其用途。 | 同一交易的各環節、事件及重試維持可識別的交易歸屬與用途。 |

這是兩類資訊的語意定義，尚未指定要建立兩個實體 context 類別、存取 API 或欄位格式。改價等操作可直接依 current identity 判定，不必為此建立交易主體。

依既有 AC 對照此定義的約束：

- 只讀 `currentuser.isTest` 可以表達身分方面的判斷，但不足以涵蓋交易方面的判斷。依 AC-TIP-013，即使由正式系統身分處理 test 訂單，也須維持 test 業務限制。
- 執行身分與交易描述不同維度，兩者用途不同不自動等於 AC-TIP-014 的用途矛盾；各自須能明確判定，並符合該操作的規則。完整組合政策尚未定案。
- 操作不涉及交易，與交易執行途中遺失 current transaction，是不同情況；後者仍依 AC-TIP-014 視為 BUG。
- AC-TIP-012 的 test 查詢與正式預約系統到期整理，仍有明確的工作交接與責任邊界；兩端依各自責任建立執行範圍，不因機械複製或清空資訊而判定用途。具體承接格式留給後續 contract。

### 4. 使用正常 log 機制記錄 context 與判定結果

- 沿用正常 log 機制，寫入已確認 AC 要求的對應資訊。
- 特定行為的紀錄內容由 context 與該次判定結果決定；實際略過、正常執行、業務失敗沿用既有分類規則。
- 不因用途為 test 就虛構略過紀錄；AC-TIP-003 不要求失敗 log 額外帶 test 標記、查詢型報表排除不另留 TiP log 等已接受規則仍有效。
- Log 工具、保存方式與實體格式屬實作議題；由兩類 context 與實際判定結果提供已確認 AC 要求的紀錄資訊，具體欄位留給後續 contract。

### 5. 從資料定義明確表達用途

- 在 database schema 層級明確定義各種物件的正式／測試用途及其適用規則，使後續資料使用有明確依據。
- 本決策延續第一類用途不可變物件與第二類受保護物件的分類；不增加測試專屬 Product、Inventory 或 Reservation 等資料副本需求。各類物件如何在實體 schema 表達，尚未指定。
- 查詢型報表與事件型統計依已接受 AC 使用用途定義，驗收仍確認正式商業統計未受影響；schema 的定義不能取代結果驗證。

| 前輪議題 | 本輪收斂結果 |
|---|---|
| (1) 用途判定與權威來源 | 以最低層介面的不可變契約為基礎；建立權限交由應用端。既有 Member 衍生規則不變，由兩類 context 提供判定依據。 |
| (2) 用途保存與不可變性 | 規範已確認，具體保證機制列為實作議題。 |

| (4) 商業效果控制 | 應用端每個相關環節依 context 與業務政策判定，在效果發生前執行控制；完整政策矩陣留給應用規格。 |
| (5) 系統工作邊界 | 以 event-driven／task queue 等交接機制隔離兩端；用途承接仍受 AC012／013 約束。 |
