更新日期：2026-10-17。

本文件記錄依 [TiP 設計原則](tip-guidelines.md) 逐條確認的接受條件。`accepted` 代表使用者接受需求，不代表已實作或測試通過；正式 `/spec` 與 contract 的整理仍待後續階段。目前已接受 AC-TIP-001、AC-TIP-003、AC-TIP-004、AC-TIP-005、AC-TIP-006、AC-TIP-007、AC-TIP-008、AC-TIP-009、AC-TIP-010、AC-TIP-011、AC-TIP-012、AC-TIP-013、AC-TIP-014、AC-TIP-015。本輪 14 條核心 AC 已全部確認。2026-10-17 依[最新範圍決策](../decisions/2026-10-17-tip-standard-scope-and-context.md)，Cart 排除標記與會員承接，Token.IsTest 建立時由 Member.IsTest 繼承保存；AC-TIP-002 改以 PaymentId 白名單作為標準 PoC 驗收方向。PetShop 案例保留，暫不納入本輪實作。

AC-TIP-012 已依使用者修正保留並接受：測試查詢可通知系統正常處理真正逾期的正式預約。PetShop 現行結構的差距記入[架構變更事項](tip-architecture-notes.md#petshop-expiration-change)，留待實作處理。

## AC-TIP-001

**測試會員完成一般商品結帳**

狀態：accepted。確認日期：2026-10-16。包含使用者補充的略過扣款／出貨紀錄，以及商業統計驗收要求。

### Given／前提

- 註冊 Member 時，其 ID 命中預先指定的 MemberId 白名單，自動設定 IsTest = true，使用其有效 Token。
- 商品售價 100 元，對應 SKU 可用庫存為 10。
- 購買 2 件，沒有折扣；其他權限與業務條件均符合。
- 觀察期間沒有其他交易異動這筆庫存或待比對的商業統計。
- 若有商業統計功能或報表，先以固定的查詢範圍與條件記錄交易前結果，作為比較基準。

### When／操作

建立購物車、加入商品，並完成 Checkout；若有商業統計功能或報表，交易後以相同範圍與條件讀取結果。若統計由事件更新，需在相關事件處理完成後驗證。

### Then／預期結果

| 項目 | 驗收條件 |
|---|---|
| 用途傳遞 | Token.IsTest 建立時從 test Member 繼承保存；Checkout 建立時為 test。Cart 不保存用途、不承接會員。 |
| 業務檢查 | 身分、權限、商品及庫存檢查照常執行。 |
| 計算結果 | 數量為 2，訂單總額為 200 元。 |
| 訂單 | 成功建立一筆 test Order。 |
| 交易封存 | 依 2026-10-17 補充決策，Checkout 從作用中區移至封存區；保留原交易 ID、IsTest 與 PaymentId，Order 可循關聯查回。 |
| 庫存 | 可用庫存仍為 10；過程中也沒有先扣減再補回。 |
| 商品資料 | Product 與 SKU 均未異動。 |
| 扣庫存紀錄 | 留下「因 test 略過扣庫存」的 log，能對應到這次交易。 |
| 扣款 | 不發生真實扣款，並留下「因 test 略過扣款」的 log，能對應到這次交易。 |
| 出貨 | 不觸發真實出貨，並留下「因 test 略過出貨」的 log，能對應到這次交易。 |
| 查詢型商業統計／報表（若有） | 查詢排除 test Order；交易前後的正式商業統計結果不變。不要求為這種查詢排除另留 TiP log。 |
| 事件更新的商業統計（若有） | 因 test 略過統計更新並留 log，能對應到這次交易；事件處理完成後，正式統計結果仍與交易前一致。 |

統計驗收應涵蓋該功能實際提供的正式商業指標，例如正式訂單數、銷量及營收；不能只檢查 log。若兩種統計方式都存在，兩者都要驗證。未提供的統計功能標示不適用，不因本 AC 新增報表，也不將其記為測試通過。

扣款與出貨的要求仍是驗收目標；現有 PoC 沒有接上真實服務，不足以證明隔離與略過紀錄已符合 AC。本文件沒有宣稱已執行上述驗證。

## AC-TIP-002

**正式會員使用 PaymentId 白名單中的測試卡號**

狀態：範圍與建立時判定原則已接受（2026-10-17），白名單已確認預設於 code 或 database，PaymentId 僅為數值，create 當下查清單；正式 testcase 隨 code 變更同步整理。取代原「未實作信用卡時為 N/A」的示意定位；不要求新增真實信用卡服務。

### Given／前提

- 正式 Member 使用有效 Token，Token 用途跟隨 Member。
- 預先設定測試 PaymentId 白名單，選用其中一個 PaymentId。
- Cart 不標記用途、不承接會員；商品與庫存等條件符合正常結帳要求。

### When／操作

建立 Checkout 時提供該 PaymentId，建立後完成交易。

### Then／預期結果

- Member 維持正式身分；Checkout 建立時固定為 test，後續 Order 承接 test 用途。
- 正常執行身分、買方及業務檢查；不產生真實扣款、扣庫存、出貨或正式商業統計效果，實際因 test 略過的操作留 log。
- Token 仍代表正式 Member，Cart 無用途變更；本案例不以更改會員用途達成測試交易。
- 既有 Checkout／Order 不因重試或白名單調整重新分類。

此規則限於本輪標準 Checkout 建立流程；其他付款來源與所有操作的通用組合政策仍未定案。未接入真實金流不構成真實支付隔離已驗證的證據。

## AC-TIP-003

**測試會員結帳時庫存不足**

狀態：accepted。確認日期：2026-10-16。使用者確認：正常記錄庫存不足、交易終止即可；此案例只需由 Checkout 物件本身的 test 標記識別測試用途，不要求另加特殊的 test 失敗紀錄。

### Given／前提

- Member 與 Checkout 為 test，Token 跟隨 Member；Cart 不保存用途。
- 商品單價 100 元，可用庫存只有 1 件，購買數量為 2 件。
- 身分、權限及其他業務條件均符合。
- 觀察期間沒有其他交易影響庫存或商業統計。

### When／操作

執行完成 Checkout。

### Then／預期結果

| 項目 | 驗收條件 |
|---|---|
| 庫存檢查 | 照常檢查，判定庫存不足。 |
| 結帳結果 | 回傳庫存不足，終止本次結帳流程。 |
| 訂單 | 不建立 Order，包括 test Order。 |
| Checkout | 保留原 Checkout，維持 test 用途，沿用既有失敗處理規則。 |
| 受保護資料 | 庫存維持 1，Product／SKU 不變。 |
| 後續流程 | 不啟動後續扣款、出貨或訂單成立事件。 |
| Log | 按照正常流程記錄庫存不足及交易終止；測試用途由 Checkout 物件的 test 標記識別，不要求 log 額外帶 test 標記。 |
| 商業統計 | 若有相關功能或報表，驗證正式訂單數、銷量、營收均未受影響。 |

此流程因正常業務檢查失敗而終止，未走到扣庫存、扣款或出貨的操作判定點，不產生「因 test 略過」這些操作的 log。這與 AC-TIP-001 通過檢查後、因 test 略過商業效果的情況不同。

## AC-TIP-004

**物件建立後，不得變更正式／測試用途**

狀態：accepted。確認日期：2026-10-16。

### Given／前提

分別準備正式與 test 的 Order、Member、Checkout、Token。這四種標記物件都必須驗證以下兩個方向；Token.IsTest 建立時由 Member.IsTest 繼承保存，且維持一致。Cart 不列入本案例。

### When／操作

嘗試變更同一物件的用途：

| 原用途 | 要求變更為 | 預期結果 |
|---|---|---|
| 正式 | test | 拒絕變更，維持正式。 |
| test | 正式 | 拒絕變更，維持 test。 |

### Then／預期結果

- 重新讀取物件，確認原用途未變。
- 關聯物件的用途也沒有因此改變。
- 正常記錄「用途不可變更」的拒絕原因。
- 其他合法的業務欄位更新，仍依原有規則處理；不可變的限制只針對用途分類。

## AC-TIP-009

**正式與測試交易同時結帳，效果各自隔離**

狀態：accepted。確認日期：2026-10-16。

### Given／前提

- 同一商品單價 100 元，庫存 10 件，沒有折扣。
- 正式會員 A 購買 3 件；測試會員 B 購買 2 件。
- 各自使用有效 Token、不同 Cart 及自己的 Checkout；Token 跟隨 Member，Checkout 用途正確，Cart 無用途分類。
- 兩筆交易均符合成功條件，沒有其他交易干擾。

### When／操作

兩位會員同時發起完成 Checkout，等待兩筆操作及相關事件處理完成。

### Then／預期結果

| 項目 | 驗收條件 |
|---|---|
| 正式訂單 | A 建立一筆正式 Order，金額 300 元。 |
| 測試訂單 | B 建立一筆 test Order，金額 200 元。 |
| 庫存 | 最終為 7 件，僅正式交易扣除 3 件；測試交易全程不扣庫存。 |
| 正式流程 | A 的付款、履約依正常規則處理，不受 B 的 test 用途影響。 |
| 測試流程 | B 略過真實扣款、扣庫存、出貨，分別留下對應 log。 |
| 商業統計（若有） | 正式訂單數只增加 1、銷量只增加 3、營收只增加 300 元。 |
| 事件統計（若有） | 正式事件正常更新；測試事件略過更新並留 log。 |

本案例驗證同一套服務同時處理兩種交易時，測試模式不會影響另一筆正式交易，也不會遺漏自身的效果控制。

## AC-TIP-010

**測試會員操作購物車，可正常新增、刪除商品**

狀態：accepted。確認日期：2026-10-16。

### Given／前提

- Member 為 test，Token 跟隨 Member；Cart 目前為空，不保存用途、不承接會員。
- 商品有效，售價 100 元、庫存 10 件。
- 身分、權限及其他業務條件均符合。

### When／操作

1. 加入該商品 2 件，重新讀取 Cart。
2. 刪除剛才新增的購物車明細，再次讀取 Cart。

### Then／預期結果

| 項目 | 驗收條件 |
|---|---|
| 新增結果 | 實際保存到 Cart；重新讀取可看到該明細，數量為 2。 |

| Log | 沿用正常操作紀錄規則，不將已實際執行的 Cart 異動記成「因 test 略過」。 |

本案例確認 Cart 排除用途分類後，測試會員的購物車操作仍正常保存；不因身分為 test 略過 Cart 寫入。

## AC-TIP-011

**測試會員不能完成其他會員的 Checkout**

狀態：accepted。確認日期：2026-10-16。

### Given／前提

- A、B 是不同的 test Member，各有自己的 test Token。
- B 已使用一個 Cart 建立自己的 test Checkout；Cart 本身不保存用途或會員綁定。
- 商品、庫存及其他結帳條件均符合。

### When／操作

A 使用自己的有效 Token，嘗試完成 B 的 Checkout。

### Then／預期結果

| 項目 | 驗收條件 |
|---|---|
| 權限檢查 | 正常拒絕，回傳既有的 `BuyerMismatch`；HTTP API 對應 `403 Forbidden`。 |
| Checkout／Cart | Checkout 內容、買方與 test 用途不變；所引用的 Cart 內容保留，Cart 無用途或會員綁定。 |
| 訂單 | 不建立任何 Order，包括 test Order。 |
| 商業效果 | 不扣庫存、不扣款、不出貨、不觸發訂單完成事件；既有商業統計不變。 |
| Log | 正常記錄買方不符、交易遭拒；未走到的操作不留下「因 test 略過」紀錄。 |

本案例確認即使雙方都是 test，仍須遵守原本的身分與權限規則。

## AC-TIP-012

**測試查詢發現正式預約逾期，由系統正常清理**

狀態：accepted。確認日期：2026-10-16。依使用者修正保留本案例，取代原先「因 test 略過到期寫入」的未接受草案；現行 PetShop 架構差距留待實作處理。

### Given／前提

- 正式會員 A 已建立預約及其衍生 Product；Reservation 的持久化狀態仍為 `Holding`。
- `HoldExpiresAt` 為 12:00，系統評估時間固定為 12:01，預約時段尚未開始。
- B 是 test Member，使用自己的有效 test Token 查詢該預約商品；查詢符合既有存取規則。
- 本案例的到期通知／事件未列為受保護對象，允許由測試查詢觸發。
- 沒有其他操作變更該預約、商品或時段占用；查詢與系統清理均使用上述評估時間。

### When／操作

1. B 依 Product ID 查詢商品，系統發現 A 的預約已逾期。
2. 查詢流程發出到期通知／事件，交由系統執行清理；事件不代表 B 要求執行會員業務操作。
3. 等待對應的系統清理處理完成，再讀取持久化結果。

### Then／預期結果

| 項目 | 驗收條件 |
|---|---|
| 查詢結果 | 正常判定預約已逾期，不回傳可購買商品；沿用既有商品不可用結果。 |
| 到期通知 | 正常發出，不因查詢者 B 為 test 而略過；通知的業務執行主體不綁定 B。 |
| 系統清理 | 系統依正式預約資料與到期規則正常處理，不因發現者 B 為 test 而略過到期更新。 |
| Reservation | 系統清理完成後，A 的預約持久化為 `Expired`，`UpdatedAt` 依正常到期整理規則更新；歸屬仍為 A。 |
| Product 與歷史資料 | 預約及 Product 紀錄保留，Product 內容不變；本案例的「清理」為狀態更新，不增加實體刪除需求。 |
| 時段可用性 | 依到期時間，該 hold 已不占位；不必等待狀態寫回才判定失效，也不因 B 為 test 而延長保留期限。 |
| Log | 沿用正常查詢與系統清理的紀錄規則，不將實際完成的到期整理記成「因 test 略過」。 |

本案例區分「測試會員發現逾期」與「系統執行正式資料的生命週期整理」。這項系統責任不解除其他測試業務操作對受保護物件的限制。

事件傳遞、系統執行 context、完成判定及 PetShop 重構需求列於[架構變更事項](tip-architecture-notes.md#petshop-expiration-change)。本 AC 已接受不代表現行同步 lazy expiration 已符合所需的執行邊界。

## AC-TIP-013

**測試訂單的後續事件與重試維持測試用途**

狀態：accepted。確認日期：2026-10-16。與 AC-TIP-014、AC-TIP-015 一併確認。

### Given／前提

- 已依 AC-TIP-001 建立一筆 test Order，原 HTTP request 已結束。
- 該訂單的後續業務事件由背景工作或系統處理；訂單用途可明確判定為 test。
- 記錄處理前的庫存、付款／出貨紀錄及既有正式商業統計；沒有其他操作干擾。

### When／操作

處理該事件，並再次重送同一事件或重試其後續工作；等待相關處理完成。

### Then／預期結果

- 首次處理及重送／重試時，衍生業務行為均明確維持 test，不因原 request 已結束或處理者為系統而轉成正式。
- 必要的權限及業務檢查照常；test Order 的用途不變，允許的內部處理仍依既有規則執行。
- 不扣真實款項、不扣庫存、不出貨，受保護資料不變。
- 若有正式商業統計或報表，其結果不變；若有事件型統計更新，因 test 略過並留 log。
- 每次實際走到因 test 而略過的商業操作，均留下對應原因與 log。未執行到的操作不虛構略過紀錄；本 AC 不規定重複事件必須執行幾次。

本案例涵蓋測試訂單衍生的業務效果；AC-TIP-012 已明確定義的正式預約系統到期整理，仍依其自身規則執行。

## AC-TIP-014

**用途必須明確；用途遺失或衝突屬於 BUG**

狀態：accepted。確認日期：2026-10-16。與 AC-TIP-013、AC-TIP-015 一併確認。

### Given／前提

- 準備用途已明確確定的正式與 test 交易，相關物件均依規則建立。
- 觀察入口、內部呼叫、事件處理及重試等實際存在的執行邊界。

### When／操作

分別執行正式與 test 流程，在各執行邊界檢查系統判定的用途與既定用途是否一致。

### Then／預期結果

- 每個需要用途判定的操作都能明確識別其用途，正式與 test 不混淆；測試衍生業務流程不得遺失或改變用途。
- 若出現無法判定、用途遺失或相互矛盾，該次驗收失敗並視為 BUG，不當作可接受的正常業務分支。
- 不得靠默認正式、任意選擇用途或將不明用途當作「因 test 略過」來讓驗收通過。
- 若在錯誤注入中刻意製造上述異常，應回報系統錯誤並阻止用途不明的操作產生商業效果；即使成功阻止副作用，也不能把用途不明當成正常狀態。

AC-TIP-012 的系統到期整理有明確的執行責任，不屬於用途遺失。此案例驗證可判定性與一致性；context、來源組合、錯誤代碼及診斷格式留待架構設計。

## AC-TIP-015

**測試預約略過建立後，不接續該預約的購物車與結帳**

狀態：accepted。確認日期：2026-10-16。與 AC-TIP-013、AC-TIP-014 一併確認。

### Given／前提

- test Member 使用有效 test Token，選擇可預約的服務、時段、場地與人員。
- 必要身分、權限與業務條件均符合，沒有其他操作干擾。

### When／操作

執行預約流程的 `CreateHold`，必要檢查通過後，依 AC-TIP-007 略過建立 Reservation 與衍生 Product。

### Then／預期結果

- 不建立 Reservation 或衍生 Product，不占用正式時段資源。
- 此預約流程到此停止，不把未建立的預約商品加入 Cart，不為該預約建立 Checkout 或 Order，包括 test Order。
- 不以臨時或虛構商品接續結帳，也不將略過結果當作已建立可購買的預約。
- 既有 Cart 內容不變，Cart 本身不保存用途；同一測試會員仍可依 AC-TIP-001、AC-TIP-010 操作一般商品。
- 保留 AC-TIP-007 的略過預約建立與衍生 Product 紀錄；未走到的扣庫存、扣款、出貨不產生 test 略過 log。

回應如何讓 API／CLI／UI 辨識「測試預約未建立、流程不接續」，沿用既有架構待議事項，不在本 AC 指定 response header、result code 或畫面。
